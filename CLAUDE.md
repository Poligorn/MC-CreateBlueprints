## Кратко о проекте

Create Blueprints — аддон к Create для модпака и сервера **MC-Ikaria**. Вдохновение — чертежи EVE Online, не лор EVE.

Игрок находит редкий тировый чертёж (в основном в данжах, очень редко в обычных сундуках). Каждый чертёж делает один тип предмета: оружие, броня или инструмент. Предмет выпускается скрытой цепочкой станков Create в духе sequenced assembly. Цепочка скрыта от JEI/EMI. Скрафченный компьютер-терминал показывает только общее число шагов и число операций каждого типа (например «5 шагов: 3 прессования, 2 обжига»), без порядка, и чего не хватает линии.

Стартовый предмет — сам целевой предмет (для кирки T2 кладут кирку). Он тратится на каждой попытке. Ручные активаторы (деплоеры) тоже тратят ресурсы; чем выше тир, тем больше и дороже.

После каждого прогона терминал пишет процент исследования: доля шагов, стоящих на своих местах. Усиленный предмет выдаётся только при 100%. Всё, что меньше, даёт хлам. Процент — только обратная связь, он не масштабирует предмет.

Копии, перегрев, T4–T5, рынок и структуры — не MVP. Они описаны в `docs/DESIGN.md` и `docs/ROADMAP.md`.

Рабочее имя продукта — **Create Blueprints**. Внутренний `mod_id` репозитория сейчас `blueprintforge`, отображаемое имя — «Blueprint Forge». Не переименовывать id без явного OK Егора: это ломает сохранения.

## Сборка и тесты

Нужна Java 21. Зависимости качает Gradle.

| Команда | Что делает |
|---|---|
| `./gradlew test` | JUnit |
| `./gradlew build` | Jar и JUnit |
| `./gradlew runGameTestServer` | Гейм-тесты в мире с Create; ненулевой код при провале |
| `./gradlew runServer` | Выделенный сервер в `run/` (нужен `run/eula.txt` с `eula=true`) |
| `./gradlew runClient` | Клиент для ручной проверки |

Гейм-тесты живут в source set `src/gametest` и в игровой jar не попадают. В dev-запусках в логе есть ошибки загрузки тестового datapack `blueprintforge_test` — на `main` это три или четыре намеренно битых файла. Так задумано, в jar игрока их нет.

На `main` гейм-тесты сейчас проверяют старый Архив (например `/test run beltcarriesitemsthroughthearchive`, `/test run archiveremakesaplainswordandkeepstheoriginal`). Новые тесты именуй по проверяемому поведению новой концепции. В dev-клиенте сцены строятся командой `/test run <имя>`. Имена методов в `src/gametest/java/.../BlueprintForgeGameTests.java` NeoForge приводит к нижнему регистру без подчёркиваний.

Серверный конфиг на `main`: `config/blueprintforge-server.toml`.

Сборку и GameTests этой сессии подготовки пакета я не прогонял. Перед выводами «зелёное» их нужно реально запустить.

## Соглашения по коду

- Java 21, кодировка UTF-8, идентификаторы и комментарии в коде — на английском (как в текущем репозитории).
- Игроку видимые строки — в `en_us.json` и `ru_ru.json` сразу, без хардкода.
- Контент и числа баланса — в datapack JSON, не в Java. Код читает данные и падает мягко: битый JSON не роняет сервер, ошибка пишется в лог, остальной пакет грузится.
- Состояние предмета — через data components 1.21.1, не через NBT-хаки в стиле 1.20.
- Миксины — крайняя мера, только пакет `compat.create`, один компонент, с записью «почему публичного API не хватило». Код Create не копировать и не декомпилировать. Sable не читать. Это правило карточки спайка `Agmz84v6`.
- JUnit — на чистую логику (генератор цепочки, процент по позициям, загрузка JSON). GameTests — на поведение в мире с Create.
- Не добавлять зависимости без нужды. JEI/EMI в MVP не подключать: цепочка должна быть скрыта, а не документироваться в просмотрщике.
- Секреты, ключи и токены в репозиторий и в чат не попадают.

## Definition of done

Задача считается сделанной, только если:

1. Критерии приёмки из `docs/MVP_TASKS.md` (или из карточки Trello, если задача оттуда) выполнены.
2. `./gradlew test` и `./gradlew build` проходят. Если затрагивается поведение в мире — ещё `./gradlew runGameTestServer`.
3. В описании PR честно написано, что прогнано, а что нет (клиент, сервер, конкретный станок Create, JEI). Не утверждать проверенным то, что не запускалось.
4. Есть строки `en_us` и `ru_ru` для нового пользовательского текста.
5. Новые числа и контент живут в datapack, если для них уже есть схема.
6. В предметах и GUI использованы только официальные ассеты из `assets/` этого пакета (см. `assets/README.md` и каталог `assets/blueprints/`). Свои пиксели вместо официальных иконок не рисовать. Макеты из `assets/mockups/terminal/` в ресурсы релиза не копировать.
7. Работа идёт в ветке и оформлена как PR в `main`. PR не смержен, тега и релиза нет.

## Жёсткие правила

1. **Только ветки и PR.** Никогда не мержить, не ставить тег и не делать release / publication. Даже если CI зелёный, даже если задача «кажется готовой».
2. **Никаких секретов** в коде, коммитах, логах и сообщениях.
3. **Только официальный арт.** Источник: `assets/` пакета (логотип, `blueprint_item.png`, тиры и типы; полный каталог вариантов — `assets/blueprints/`). Макеты терминала v1/v2 и блок терминала — **прототипы** (`docs/terminal/`, `assets/mockups/terminal/`), не финальный арт. Их нельзя считать утверждёнными текстурами для релиза; v2 и блок нужно переделать позже.
4. **Всё настраивается datapack JSON.** Не зашивать новые типы, тиры, шаги и пулы ресурсов в код.
5. **Не делать новое UI без утверждённого макета.** Для MVP допустим простой рабочий экран терминала (карточка `hmZn6lNE`): слоты и текст, без финального «компьютерного» оформления. Макеты v2 можно использовать как ориентир раскладки, но нельзя переносить как есть: на них есть уже отменённые решения (см. DESIGN.md, раздел конфликтов). Финальный GUI — в 1.0 и только после OK Егора.
6. **Честно писать, что не проверено.**
7. Не пушить в `main`, не закрывать и не мержить чужие PR, не менять Trello, если Егор об этом отдельно не попросил.
8. Одна задача = одна ветка = один PR, по `docs/MVP_TASKS.md`. Не хватать следующую крупную задачу в том же PR, если она не нужна для приёмки текущей.
9. Открытый вопрос из `docs/OPEN_QUESTIONS.md` не «закрывать» догадкой в коде. Если без ответа нельзя двигаться — остановиться и спросить Егора. Если ответ не блокирует, взять явно помеченный временный вариант и написать об этом в PR.
